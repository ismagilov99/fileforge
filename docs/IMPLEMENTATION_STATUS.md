# Implementation and verification status — FileForge 5.5.2

## Delivery scope

FileForge 5.5.2 is a browser-only TypeScript/Vite application with four workflows: image conversion, text export, ZIP creation and UTF-8 text merge. The UI is separated into focused modules; processing engines are isolated from DOM concerns; expensive operations use dedicated Web Workers.

The 5.5 capacity profile restores the original published application's large input values while retaining independent integrity and resource guards. The exact runtime values are defined in `src/core/config.ts` and documented in `docs/LIMITS.md`.

- Image input: PNG, JPEG, WebP, GIF, BMP and sanitized SVG. Output: PNG, JPEG and WebP. Animated sources are converted to a static image; animation preservation is not promised.
- Text export: TXT, Markdown, HTML, JSON, CSV and XML. TXT/Markdown preserve the user's entered string; structured formats add only the syntax required by the selected format.
- ZIP creation: conventional ZIP generated locally through JSZip, within configured per-file, aggregate, file-count, folder-count and output limits.
- ZIP import for merge: STORE and raw DEFLATE when `DecompressionStream('deflate-raw')` is available. ZIP64, encryption, multi-volume archives, unsupported filename encodings, unsupported flags and malformed structures fail closed.
- History stores bounded metadata only. File contents are not persisted in application history.
- The central folder-entry ceiling is shared by ZIP creation and ZIP import through one `MAX_ZIP_FOLDERS` constant (150).

## 5.5.2 changes from 5.5.1

- Fixed the reported ZIP import defect: folder entries are rejected only when `directoryCount > LIMITS.merge.maxFolders`; the message uses the same configuration value. The former hardcoded `100` is removed from active code.
- Added tests for exactly 150 explicit folder entries (accepted), 151 (rejected) and matching archive/merge folder configuration.
- Rejected malformed ZIP directory entries with non-zero data sizes, non-zero CRC32 or a compression method other than STORE. The bounded extractor repeats the directory metadata check if it is called with a supplied entry object.
- Fixed merge preflight so unsupported non-text entries in a ZIP do not count against the 100 supported-text-file output cap. The archive parser still independently enforces the total ZIP file-entry limit, and actual supported entries are counted again before they are committed.
- Centralized basename-based extension detection in `getFileExtension()`. Dots in parent paths no longer affect ZIP-entry extension recognition. Extensionless `Dockerfile`/`Makefile` and dotfiles are supported where the format allowlist explicitly includes them.
- Added runtime validation of text-export and merge-export Worker payloads. Unsupported formats, non-string text, invalid Unicode, inconsistent byte-size metadata and out-of-range file counts are rejected before result creation.
- Updated `THREAT_MODEL.md` so it no longer describes the superseded 5.4 reduced capacity profile.

## Checks actually performed for 5.5.2

- **Strict TypeScript source check:** passed with no diagnostics for all files under `src/`, using the globally installed TypeScript 5.8.3 compiler and temporary ambient declarations for unavailable external dependencies (`dompurify` and `jszip`). This verifies internal source typing but does not replace the pinned TypeScript 7.0.2 run against real package declarations.
- **Independent runtime harness:** 20 checks passed against transpiled core/engine modules under Node 22.16.0. Coverage included basename extension parsing, unknown runtime format rejection, non-string text rejection, merge metadata-size validation, merge file-count boundary, exact TXT output size, HTML escaping, ZIP STORE extraction, raw DEFLATE extraction, exactly 150 explicit ZIP directories accepted, 151 rejected with the configured message, malformed directory CRC rejection, forged STORE-size rejection before allocation, extraction bounds, CRC mismatch rejection and an integration case proving that an unsupported PNG entry does not consume the 100 supported-text merge slots.
- The runtime harness loads `validation.ts` through a temporary DOMPurify stub solely to permit Node module loading. It **does not** verify real DOMPurify SVG sanitization, native browser DOM parsing or image decoding.
- ZIP fixtures in the runtime harness were built using Node's built-in raw-DEFLATE implementation. This is not a substitute for testing ZIPs generated by the pinned JSZip package in a browser.
- The source contains **115 Vitest `it(...)` declarations** and **16 Playwright test declarations** at this delivery. Their presence is not evidence that the runners pass.
- The project manifest was regenerated and verified. The delivered ZIP was integrity-checked; every file in it was compared byte-for-byte with the project tree. The full-source Markdown was generated from every project file and checked for file coverage.

## Checks not executed / release blockers

- No `package-lock.json` is present. It was not fabricated manually.
- The authoring environment has Node 22.16.0 and npm 10.9.2, while the project intentionally pins Node 24.22.3 and npm 11.19.1. The npm registry/cache was not available, so the pinned toolchain could not be installed here.
- `npm ci`, pinned TypeScript 7.0.2, Vitest, Biome lint/format, Vite production build, post-build CSP verification, `npm audit` and SBOM generation were not executed.
- Playwright/axe was not run against Chromium, Firefox or WebKit. No physical Android/iOS or cross-browser check was performed.
- No real-device peak-memory, low-memory, repeated-operation, long-task or object-URL leak profiling was performed. Large browser-side limits can still lead to OS/browser-level tab termination; Workers do not create additional RAM.
- The final bundle was not deployed to GitHub Pages and no production response headers or deployed network trace were inspected.

## Reproducible release path

1. Run `.github/workflows/prepare-lockfile.yml` on a GitHub runner with access to npm registry. It uses the pinned Node/npm versions and creates a real lockfile instead of relying on a hand-written one.
2. Inspect the generated artifact, commit `package-lock.json` and regenerate/commit `MANIFEST.sha256`.
3. Require the normal CI workflow to pass: format, lint, typecheck, Vitest, Vite build, production CSP verification, Playwright/axe and npm audit.
4. Verify the deployed GitHub Pages build and run the device/memory matrix before treating the release as production-ready.

## Release decision

**Status: engineering candidate; not a verified production release.** The specific 5.5.1 ZIP-folder-limit mismatch and the additional source-level issues described above are corrected and covered by regression tests plus independent runtime checks. Do not describe FileForge 5.5.2 as Staff-level production-ready until the pinned dependency tree, real browser tests, security audit, deployed build and physical-device/resource checks are verified. Absolute zero-defect or zero-OOM guarantees are not possible for a browser-only application.
