# FileForge 5.5.2

FileForge — browser-only набор инструментов для локальной работы с файлами. В приложении четыре сценария: конвертация изображений, экспорт текста, создание ZIP и объединение UTF-8-текстовых файлов. Файлы не отправляются на сервер FileForge: обработка выполняется в текущей вкладке и выделенных Web Workers.

> **Статус поставки:** это подготовленная инженерная версия, но не подтверждённый production-релиз. В текущем комплекте намеренно отсутствует `package-lock.json`: в среде подготовки не удалось связаться с npm registry и создать достоверный lock-файл. До первой публикации необходимо выполнить установку зависимостей, зафиксировать lock-файл и пройти все release gates из этого README.

## Принципы продукта

- **По умолчанию — автоматический режим.** Если пользователь не задаёт имя или расширенные параметры, FileForge выбирает безопасные значения сам.
- **Настройки не мешают основному сценарию.** Пользовательское имя необязательно; качество изображений находится в сворачиваемых дополнительных настройках.
- **Содержимое не модифицируется незаметно.** TXT и Markdown сохраняют редакторский текст. Структурированные форматы добавляют только синтаксически необходимую оболочку.
- **Ошибка лучше некорректного результата.** Если приложение не может подтвердить тип, безопасность или целостность результата, оно не выдаёт его под неверным расширением.
- **Лимиты — часть архитектуры.** Их превышение объясняется до либо в процессе ограниченной обработки; приложение не пытается скрыть отказ запасным небезопасным путём.
- **Приватность по умолчанию.** Содержимое не сохраняется в истории и не отправляется на сервер FileForge.

## Функциональность

### 1. Изображения

Вход: PNG, JPEG, WebP, GIF, BMP (стандартные DIB 40/52/56/108/124) и SVG. Выход: PNG, JPEG и WebP. Преобразованные изображения помещаются в ZIP.

- Определение типа по сигнатуре, а не только по расширению или MIME из браузера.
- Сопоставление расширения с фактическим форматом.
- Проверка структуры IHDR/CRC PNG, стандартного DIB-заголовка и pixel offset BMP, RIFF/chunk-размеров WebP, таблицы SOF JPEG, размеров до декодирования и повторная проверка реальных размеров `ImageBitmap` в Worker.
- SVG очищается DOMPurify; при отсутствии санитайзера или сомнительной структуре файл отклоняется.
- Одно изображение декодируется и обрабатывается за раз. Предварительную проверку партии можно отменить без потери ранее добавленных файлов.
- Проверяется фактический MIME после кодирования; неподдерживаемый кодировщик не подменяется PNG.
- Точное определение дублей SHA-256 используется только для файлов до 8 MiB. Для больших изображений хеширование пропускается, чтобы не создавать дополнительную крупную копию в памяти.
- Неудачные изображения перечисляются отдельно; ZIP содержит только успешно преобразованные файлы.
- Анимированные GIF/WebP преобразуются в статичное изображение; сохранение анимации не обещается.

### 2. Текст в файл

Форматы: TXT, Markdown, HTML, JSON, CSV и XML.

- TXT и Markdown содержат ровно введённую строку: без даты, заголовка, подписи FileForge, счётчиков или других добавлений.
- HTML отображает исходный текст внутри минимального документа; специальные символы экранируются и не интерпретируются как разметка.
- JSON хранит содержимое как одну JSON-строку.
- CSV хранит содержимое в одном корректно экранированном поле. Значения, начинающиеся с `=`, `+`, `-` или `@`, некоторые табличные редакторы могут интерпретировать как формулы. FileForge сохраняет исходное значение без добавления апострофа, поэтому не открывай непроверенный CSV в табличном редакторе.
- XML помещает содержимое в корневой элемент `document`; недопустимые для XML 1.0 символы отклоняются вместо удаления.
- Непарные UTF-16-суррогаты отклоняются, чтобы браузер не заменял их незаметно на `U+FFFD`.
- Текстовый файл формируется в Web Worker. Статистика редактора пересчитывается с короткой задержкой после набора, чтобы не обходить всю строку на каждый символ при больших вставках. Для операции без измеримого промежуточного прогресса используется неопределённый индикатор, а не искусственные проценты. При CSV-экспорте показывается предупреждение о формульной интерпретации табличными редакторами; исходный текст не изменяется.

### 3. ZIP-архиватор

- Произвольные типы файлов в рамках лимитов.
- Пользовательские и автоматически создаваемые папки; пустые папки сохраняются.
- Автораскладка по типам файлов.
- Дубликаты путей разрешаются детерминированно.
- Конфликты типа «файл с именем `Docs` и папка `Docs/`» предотвращаются: конфликтующее имя файла получает суффикс.
- ZIP создаётся в Worker; итоговые MIME и размер перепроверяются до скачивания.
- ZIP-библиотека формирует результат в памяти, поэтому расширенные пределы могут требовать значительного объёма оперативной памяти устройства.

### 4. Объединение текстовых файлов

- Поддерживаются выбранные UTF-8-файлы и текстовые записи внутри обычных ZIP.
- ZIP предварительно проверяется до извлечения.
- Поддерживаются методы STORE и DEFLATE, если браузер имеет `DecompressionStream('deflate-raw')`.
- Фактический объём распаковки ограничивается потоком; проверяется CRC32.
- Один ZIP импортируется атомарно: приложение не добавляет часть записей из архива, если другая выбранная текстовая запись повреждена или имеет неверную UTF-8-кодировку.
- Неподдерживаемые форматы перечисляются как пропущенные; пользовательские файлы не меняются.
- Порядок файлов можно менять. Включение имён в результат — отдельная настройка.
- Подготовка и ZIP-импорт работают в Worker, а итоговый экспорт формируется в отдельном Worker.

## Имена файлов

Поле имени необязательно. Пустое поле означает автоматическое имя, которое показывается в предварительном просмотре и сразу обновляется при смене формата; это же имя используется при скачивании. После операции автоматически предлагается новое имя для следующего запуска. Если имя задано вручную, выбранный формат определяет расширение. Известное конфликтующее расширение заменяется с предупреждением; имя вида `report.v2` сохраняется как название версии, а не ошибочно обрезается до `report`.

Имена нормализуются по NFC, ограничиваются по размеру UTF-8, проверяются на управляющие символы, bidi-контроли, пути и зарезервированные системные имена. Содержимое самого пользовательского документа этими правилами не изменяется.

Дополнительные пределы выходных ZIP/изображений, папок, пиксельный preflight (теперь допускает полный квадрат 8 192 × 8 192, в отличие от прежнего 32-МП барьера), ограничение общего объёма merge и коэффициент распаковки — дополнительные защитные границы новой архитектуры. Они не меняют старые входные значения в сторону уменьшения. `MAX_TOTAL_SIZE=400 MiB` исходной версии использовался в загрузке изображений и архива. `MAX_FILE_SIZE=50 MiB` применялся также к обычным текстовым файлам и извлечённым записям при объединении.

Большие лимиты относятся к обработке **на устройстве пользователя**. FileForge не отправляет файлы на сервер, поэтому низкая загрузка сервера не снимает ограничения оперативной памяти, CPU и декодеров браузера. Рабочие потоки (Workers) сохраняют отзывчивость интерфейса, но не создают дополнительную память. Если устройство не выдерживает операцию, она может завершиться ошибкой браузера/ОС даже до достижения лимита приложения.

Лимиты находятся в `src/core/config.ts`; видимые подсказки интерфейса используют те же значения из конфигурации, чтобы числа не расходились. Интегритет ZIP, проверка CRC32, коэффициент распаковки, безопасные пути, сигнатуры, отказ при неподдерживаемом формате и отмена операций сохранены независимо от увеличения лимитов.

## Архитектура

```text
src/
  core/       политики, лимиты, валидация, имена, ошибки, загрузки, ZIP parser
  engines/    прикладные сценарии и обработка форматов
  workers/    изолированное выполнение тяжёлых задач
  ui/         DOM, состояние, вкладки, тема и взаимодействие
  main.ts     небольшой composition root
  style.css   визуальная система

tests/        unit- и integration-тесты
e2e/          Playwright: реальные пользовательские сценарии, загрузки и axe
 docs/        архитектура, модель угроз, доступность, производительность, поддержка браузеров
scripts/      генерация SHA-256 манифеста
.github/      CI, GitHub Pages deploy и Dependabot
```

Основные границы:

- `core` не зависит от UI.
- `engines` не обращаются к DOM.
- `workers` являются адаптерами фонового протокола и не владеют UI-состоянием.
- `ui` отображает данные только через безопасные DOM API (`textContent`, свойства элементов, Blob).
- `main.ts` только собирает модули вместе и управляет глобальной очисткой.

Подробности: [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md), [`docs/THREAT_MODEL.md`](docs/THREAT_MODEL.md), [`docs/THIRD_AUDIT_REPORT.md`](docs/THIRD_AUDIT_REPORT.md), [`docs/FOURTH_AUDIT_REPORT.md`](docs/FOURTH_AUDIT_REPORT.md), [`docs/FIFTH_AUDIT_REPORT.md`](docs/FIFTH_AUDIT_REPORT.md).

## Установка

Требуются Node.js 24.22.3 или новее и npm 11.19.1 или новее. `.npmrc` включает `engine-strict=true`: установка на неподдерживаемом Node/npm должна завершаться ошибкой, а не продолжаться с неподтверждённой средой.

После того как будет создан и проверен `package-lock.json`:

```bash
npm ci
npm run dev
```

Локальный Vite-сервер по умолчанию слушает только `127.0.0.1`. Не открывайте dev-сервер в локальную сеть через `--host 0.0.0.0`, если это не требуется и вы не понимаете сетевой риск.

Если `package-lock.json` ещё отсутствует, не создавайте его вручную. После добавления исходников в GitHub откройте **Actions → Prepare dependency lock → Run workflow**. Workflow использует закреплённые Node/npm, генерирует lock-файл, выполняет проверки, формирует SBOM и загружает artifact `fileforge-release-prerequisites`. Скачайте artifact, добавьте `package-lock.json` и обновлённый `MANIFEST.sha256` в репозиторий и закоммитьте их. После этого обычные CI и Deploy workflow смогут выполнять `npm ci`. Сам workflow подготовки зависимостей требует доступа GitHub runner к npm registry; его успех не гарантирован до фактического запуска.


Полная локальная проверка:

```bash
npm run verify
```

`verify` запускает проверку манифеста, форматирования, линтер, typecheck, unit/integration tests, production build с проверкой production CSP, Playwright E2E и `npm audit` с блокировкой любых опубликованных уровней серьёзности.

## Тестовая инфраструктура

- Vitest: имена, валидация, экспорт, ZIP parser/CRC32/DEFLATE/data descriptors, импорт и создание ZIP, история и обработка изображений.
- Playwright: E2E выполняется по production-сборке через `vite preview`, а не по dev-серверу. Сначала запустите `npm run build`. Сценарии проверяют TXT с точными байтами, HTML escaping, автоматическое имя, склейка файлов, DEFLATE ZIP import, создание ZIP, image Worker, фактические скачивания, отмена задачи и узкий viewport.
- axe-core: автоматическая проверка серьёзных/критических нарушений доступности.
- CSP source tests: проверка, что localhost WebSocket доступен только в Vite serve mode, а production policy остаётся same-origin.
- Biome: форматирование и lint.
- GitHub Actions: lockfile guard, manifest, форматирование, lint, typecheck, unit tests, build, npm audit, E2E и CycloneDX SBOM. Отдельный manual workflow подготавливает lock-файл в совместимой среде.

Наличие тестов не означает, что они уже выполнены. Текущий статус последней фактической проверки приведён в [`docs/IMPLEMENTATION_STATUS.md`](docs/IMPLEMENTATION_STATUS.md).

## Разработка и выпуск

1. Выполните workflow `Prepare dependency lock`, скачайте artifact и закоммитьте `package-lock.json` вместе с новым `MANIFEST.sha256`.
2. Запустите все команды качества локально и в чистом CI.
3. Установите браузеры Playwright и устраните все реальные провалы.
4. Проведите ручной аудит клавиатуры, скринридера, контрастности, 200% zoom и 320 CSS px.
5. Проверьте текущие Chrome, Edge, Firefox и Safari на настольных системах, Chrome Android и Safari iOS на реальных устройствах.
6. Измерьте пиковую память, долгие задачи, отмену и повторные циклы на маломощном Android и настольном компьютере.
7. Просмотрите `npm audit`, создайте SBOM командой `npm run sbom` и обновите `MANIFEST.sha256`.
8. Только после этого публикуйте GitHub Pages через `.github/workflows/deploy.yml`.

## Границы гарантий

Абсолютное отсутствие багов невозможно гарантировать. Client-side validation не является антивирусом. Браузерный image decoder и сам браузер остаются внешней границей доверия. Приложение не может обещать, что ОС не завершит вкладку при экстремальном дефиците памяти. ZIP64, multi-volume, зашифрованные ZIP и ZIP с неподдерживаемой кодировкой имён отклоняются. GIF-анимация не сохраняется в статических конвертациях. PDF/DOCX и другие офисные форматы не входят в текущий scope.

FileForge не следует считать production-ready, пока release gates не пройдены в реальном npm/CI и на поддерживаемых браузерах/устройствах.

### Content Security Policy

Production HTML restricts `connect-src` and module Workers to the same origin. The Vite development server adds only the loopback WebSocket endpoint required for HMR; that exception is not part of the production build. The policy is delivered as a meta tag because GitHub Pages does not provide arbitrary response-header configuration from this repository. FileForge also refuses to initialize inside an iframe, but that is defense in depth only; a host with configurable headers should additionally set `frame-ancestors` (or `X-Frame-Options`) and the rest of the policy as HTTP response headers.
